## 0. 핵심 원칙 (TL;DR)

1. **포맷은 도구에게**: Prettier가 자동. 사람은 로직에 집중.
2. **이름은 의도를 드러내라**: `data`, `temp`, `foo` 금지. `userProfile`, `noteList` OK.
3. **타입 없이 export 금지**: TypeScript의 모든 public API는 타입 명시.
4. **에러는 무시 X**: `try-catch` 없이 비동기 호출 금지.
5. **주석은 WHY**: "무엇을 하는가"는 코드가 말한다. "왜 그렇게 했는가"만 적는다.

**🇺🇸 English**

**Core Principles (TL;DR)**

1. **Let tools handle formatting**: Prettier runs automatically. People focus on logic.
2. **Names must reveal intent**: `data`, `temp`, `foo` are forbidden. `userProfile`, `noteList` are fine.
3. **No export without a type**: Every public API in TypeScript must have an explicit type.
4. **Never swallow errors**: Async calls without `try-catch` are forbidden.
5. **Comments explain WHY**: Code says what it does. Comments say why it was done that way.

## 2. TypeScript 공통

### 2.1 타입 vs 인터페이스

**원칙**: `type` 우선 사용. `interface`는 **확장이 필요한 클래스 계약**에만.

```typescript
// ✅
type User = {
  id: string;
  email: string;
};

type AdminUser = User & { role: 'admin' };

// ⚠️ interface는 다음과 같은 경우에만
interface IRepository<T> {
  findById(id: string): Promise<T | null>;
}
class NoteRepository implements IRepository<Note> { ... }
```

**🇺🇸 English**

**2.1 `type` vs `interface`**

Prefer `type` for everything. Use `interface` only for class contracts that need to be implemented or extended (e.g., repository patterns).

### 2.2 `any` 금지 (`unknown` 사용)

```typescript
// ❌
function parse(input: any) { ... }

// ✅
function parse(input: unknown) {
  if (typeof input === 'string') { ... }
}

// ✅ 외부 라이브러리가 any 반환 시
const data = (await axios.get('/x')).data as User;
```

**🇺🇸 English**

**2.2 No `any` — use `unknown`**

`any` disables type safety. Use `unknown` and narrow with type guards. When an external library returns `any`, cast at the call site with `as`.

### 2.3 함수 시그니처는 항상 명시

```typescript
// ❌
function createNote(title, content) { ... }

// ✅
function createNote(title: string, content: string): Promise<Note> { ... }
```

**🇺🇸 English**

**2.3 Always annotate function signatures**

All parameters and return types must be explicitly typed. No implicit `any` from missing annotations.

### 2.4 nullable 처리

```typescript
// ✅ 명시적 null
type Folder = {
  id: string;
  parent_id: string | null;
};

// ❌ undefined와 null 섞기
type Bad = {
  parent_id?: string | null;  // 두 가지 의미?
};
```

**🇺🇸 English**

**2.4 Nullable handling**

Use explicit `string | null` for values that may be absent. Do not mix `?` (optional/undefined) with `| null` on the same field — pick one semantic.

## 3. 명명 규칙 (Naming)

### 3.1 케이스

| 종류 | 케이스 | 예시 |
|---|---|---|
| **변수·함수** | `camelCase` | `noteList`, `getCurrentUser` |
| **타입·클래스·컴포넌트** | `PascalCase` | `NoteEditor`, `User` |
| **상수** | `UPPER_SNAKE_CASE` | `MAX_NOTE_LENGTH = 50000` |
| **파일 (컴포넌트)** | `PascalCase.tsx` | `NoteEditor.tsx` |
| **파일 (일반 ts)** | `camelCase.ts` | `noteService.ts` |
| **폴더** | `kebab-case` | `link-parser/` |
| **CSS 클래스** | `kebab-case` | `note-card` |
| **DB 필드** | `snake_case` | `user_id`, `created_at` |
| **API URL** | `kebab-case` 복수형 | `/api/v1/notes`, `/folders/:id` |

**🇺🇸 English**

**3.1 Casing Conventions**

| Kind | Case | Example |
|---|---|---|
| **Variables & functions** | `camelCase` | `noteList`, `getCurrentUser` |
| **Types, classes, components** | `PascalCase` | `NoteEditor`, `User` |
| **Constants** | `UPPER_SNAKE_CASE` | `MAX_NOTE_LENGTH = 50000` |
| **Component files** | `PascalCase.tsx` | `NoteEditor.tsx` |
| **General TS files** | `camelCase.ts` | `noteService.ts` |
| **Folders** | `kebab-case` | `link-parser/` |
| **CSS classes** | `kebab-case` | `note-card` |
| **DB fields** | `snake_case` | `user_id`, `created_at` |
| **API URLs** | `kebab-case`, plural | `/api/v1/notes`, `/folders/:id` |

### 3.2 의미 있는 이름

✅:
```typescript
const filteredActiveNotes = notes.filter((n) => !n.is_archived);
function findUserByEmail(email: string): Promise<User | null> { ... }
```

❌:
```typescript
const list = notes.filter((n) => !n.is_archived);   // 무슨 list?
function find(e: string) { ... }                      // 무엇을 find?
```

**🇺🇸 English**

**3.2 Meaningful Names**

Names must communicate purpose. Avoid single-letter variables, generic nouns (`list`, `data`), and abbreviated parameters outside tiny lambda scopes.

### 3.3 Boolean 이름

`is`, `has`, `can`, `should` 접두사:

```typescript
const isLoggedIn = !!user;
const hasPermission = checkAcl(...);
const canEdit = user.id === note.user_id;
const shouldRetry = error.code === 'TIMEOUT';
```

**🇺🇸 English**

**3.3 Boolean Naming**

Prefix boolean variables and props with `is`, `has`, `can`, or `should` to make the true/false meaning immediately clear.

### 3.4 함수 동사

| 동사 | 의미 |
|---|---|
| `get` | 동기 조회 |
| `fetch` | 비동기 조회 (네트워크) |
| `find` | 검색 (없으면 null) |
| `create` / `add` | 생성 |
| `update` / `set` | 수정 |
| `delete` / `remove` | 삭제 |
| `parse` | 변환 |
| `validate` | 검증 |
| `handle` | 이벤트 처리 (`handleClick`) |
| `on` | 이벤트 props (`onClick`) |

**🇺🇸 English**

**3.4 Function Verb Conventions**

| Verb | Meaning |
|---|---|
| `get` | Synchronous read |
| `fetch` | Async read (network) |
| `find` | Search — returns null if not found |
| `create` / `add` | Create new resource |
| `update` / `set` | Modify existing resource |
| `delete` / `remove` | Delete resource |
| `parse` | Transform / convert |
| `validate` | Check validity |
| `handle` | Event handler (`handleClick`) |
| `on` | Event prop passed to child (`onClick`) |

## 4. Frontend (React / Vite)

### 4.1 컴포넌트 작성 규칙

```tsx
// ✅ 1파일 1컴포넌트, named export, props 타입 inline
type NoteCardProps = {
  note: Note;
  onClick: (id: string) => void;
};

export function NoteCard({ note, onClick }: NoteCardProps) {
  return (
    <article
      className="cursor-pointer rounded-lg border p-4 hover:shadow-md"
      onClick={() => onClick(note.id)}
    >
      <h3 className="text-lg font-semibold">{note.title}</h3>
      <p className="mt-2 line-clamp-2 text-sm text-gray-600">{note.preview}</p>
    </article>
  );
}
```

```tsx
// ❌ default export, 타입 누락, 인라인 스타일
export default function NoteCard(props) {
  return <div style={{ padding: 16 }} onClick={props.onClick}>{props.note.title}</div>;
}
```

**🇺🇸 English**

**4.1 Component Rules**

One component per file. Always use named exports. Declare props as an inline `type` above the component. No `default export` for components. No inline style objects — use CSS classes.

### 4.2 Hook 규칙

```tsx
// ✅ 커스텀 훅은 use 접두사
function useNotes(folderId?: string) {
  const [notes, setNotes] = useState<Note[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    setIsLoading(true);
    fetch(folderId ? `/notes?folder_id=${folderId}` : '/notes')
      .then((r) => r.json())
      .then((data) => setNotes(data.items ?? []))
      .catch((e) => setError(e))
      .finally(() => setIsLoading(false));
  }, [folderId]);

  return { notes, error, isLoading };
}
```

훅 규칙:
- 조건문 안에서 호출 금지
- 컴포넌트 최상단에 모아두기
- 의존성 배열 정확히 (`exhaustive-deps` 린트 활성)

**🇺🇸 English**

**4.2 Hook Rules**

Custom hooks must be prefixed with `use`. Data fetching uses the native `fetch` API with `useState`/`useEffect` (no SWR). Never call hooks inside conditionals or loops. Collect all hook calls at the top of the component body. Dependency arrays must be complete (`exhaustive-deps` lint rule is active).

### 4.3 Props 컨벤션

```tsx
// 이벤트 핸들러: on{Event}
type ButtonProps = {
  onClick?: () => void;
  onDoubleClick?: () => void;
};

// children은 명시
type ModalProps = {
  open: boolean;
  children: React.ReactNode;
};

// optional은 ? + default
function Button({ size = 'md', variant = 'primary', children }: ButtonProps) { ... }
```

**🇺🇸 English**

**4.3 Props Conventions**

Event handler props follow `on{Event}` naming. Always declare `children: React.ReactNode` explicitly. Optional props use `?` and must have a default value in the destructuring.

Each feature folder follows the structure above: main component, sub-components, a `hooks/` subfolder, a `utils/` subfolder, and an `index.ts` re-export barrel.

### 4.5 스타일링 (CSS Modules / clsx)

- 클래스 길어지면 `clsx` 헬퍼 사용

**4.5 Styling (CSS Modules / clsx)**


**4.6 Import Order**

### 4.7 조건부 렌더링

```tsx
// ✅
{isLoading && <Spinner/>}
{error && <ErrorState onRetry={retry}/>}
{!isLoading && !error && notes.length === 0 && <EmptyState/>}
{!isLoading && !error && notes.map((n) => <NoteCard key={n.id} note={n} onClick={...}/>)}
```

→ 패턴이 많으면 컴포넌트로 분리 (`<AsyncList state={...}/>`).

**🇺🇸 English**

**4.7 Conditional Rendering**

Use short-circuit `&&` expressions for inline conditionals. When the branching logic grows complex, extract it into a dedicated component (e.g., `<AsyncList state={...}/>`).

### 4.8 Tiptap 에디터 컨벤션

Yggdrasil의 핵심 편집기는 **Tiptap 3** 기반입니다.

- 커스텀 Extension은 `features/editor/extensions/` 에 위치
- Extension 파일명: `PascalCase.extension.ts`
- `editor.commands.*` 호출은 항상 반환값(boolean) 체크
- 에디터 인스턴스는 컴포넌트에서 직접 생성하지 않고 `useEditor` 훅으로만 접근

```tsx
// ✅
const editor = useEditor({
  extensions: [StarterKit, MentionExtension, TagExtension],
  content: note.content,
});

// ❌ 에디터를 ref나 state로 직접 관리
const editorRef = useRef<Editor | null>(null);
```

**🇺🇸 English**

**4.8 Tiptap Editor Conventions**

Yggdrasil's core editor is built on **Tiptap 3**. Custom extensions live in `features/editor/extensions/` and are named `PascalCase.extension.ts`. Always access the editor instance via the `useEditor` hook — never store it in a `ref` or `state` directly. Check the boolean return value of every `editor.commands.*` call.

**🇺🇸 English**

**5.1 Layer Separation**

Route handlers must only wire middleware and delegate to controllers. Business logic lives in services. Database access lives in repositories. Never mix these responsibilities in a single layer.

### 5.2 에러 처리

```typescript
// utils/AppError.ts
export class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
    public details?: unknown,
  ) {
    super(message);
  }
}

// services에서
if (!note) throw new AppError(404, 'NOT_FOUND', '노트를 찾을 수 없습니다.');
if (note.user_id !== userId) throw new AppError(403, 'FORBIDDEN', '권한이 없습니다.');

// middlewares/errorHandler.ts
export const errorHandler: ErrorRequestHandler = (err, req, res, next) => {
  if (err instanceof AppError) {
    return res.status(err.statusCode).json({
      success: false,
      error: { code: err.code, message: err.message, details: err.details },
    });
  }
  console.error(err);
  res.status(500).json({
    success: false,
    error: { code: 'INTERNAL_ERROR', message: '서버 오류가 발생했습니다.' },
  });
};
```

**🇺🇸 English**

**5.2 Error Handling**

Throw `AppError` from services with an HTTP status code and a machine-readable `code` string. The central `errorHandler` middleware converts `AppError` instances to JSON responses and logs unexpected errors.

### 5.3 입력 검증 (Express validator / 수동 검증)

```typescript
// middlewares/validate.ts — 직접 구현 예시
export const validate =
  (schema: { parse: (data: unknown) => unknown }) =>
  (req: Request, _res: Response, next: NextFunction) => {
    try {
      req.body = schema.parse(req.body);
      next();
    } catch (err) {
      next(new AppError(400, 'VALIDATION_ERROR', '입력값이 올바르지 않습니다.', err));
    }
  };
```

> 검증 라이브러리는 팀 합의 후 선택. 현재 zod 미포함 — 필요 시 추가.

**🇺🇸 English**

**5.3 Input Validation**

All external input must be validated before reaching the service layer. The `validate` middleware wraps any schema with a `.parse()` method (e.g., a hand-rolled validator or a library adopted by team consensus). zod is not a declared dependency of this project — do not add it without a team decision.

### 5.4 비동기 코드

```typescript
// ✅ async/await + try-catch
async function getNote(id: string): Promise<Note> {
  try {
    const note = await Document.findById(id);
    if (!note) throw new AppError(404, 'NOT_FOUND', 'Not found');
    return note;
  } catch (err) {
    if (err instanceof AppError) throw err;
    throw new AppError(500, 'INTERNAL_ERROR', 'DB error', err);
  }
}

// ❌ Promise then 체인 (가독성 떨어짐)
function getNote(id) {
  return Document.findById(id).then((n) => n).catch((e) => null);
}
```

**🇺🇸 English**

**5.4 Async Code**

Always use `async/await` with `try-catch`. Promise `.then()` chains are not permitted — they make error propagation harder to follow. Re-throw `AppError` instances as-is; wrap unknown errors in a new `AppError(500, ...)`.

### 5.5 환경변수

```typescript
// config/env.ts
const envSchema = {
  NODE_ENV: process.env.NODE_ENV ?? 'development',
  PORT: Number(process.env.PORT ?? 4000),
  MONGO_URI: process.env.MONGO_URI!,
  JWT_SECRET: process.env.JWT_SECRET!,
  JWT_EXPIRES_IN: process.env.JWT_EXPIRES_IN ?? '7d',
  CORS_ORIGIN: process.env.CORS_ORIGIN!,
};

export const env = envSchema;
// 사용: env.MONGO_URI (타입 안전)
```

> 🚨 `process.env`를 직접 참조 X. 위처럼 한 곳에서 검증 후 export.

**🇺🇸 English**

**5.5 Environment Variables**

Never access `process.env` directly in application code. Centralise all env reads in `config/env.ts`, validate/coerce there, and export a typed `env` object. This makes misconfiguration fail loudly at startup.

### 5.6 로깅

```typescript
import winston from 'winston';

export const logger = winston.createLogger({
  level: env.NODE_ENV === 'production' ? 'info' : 'debug',
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.json(),
  ),
  transports: [
    new winston.transports.Console(),
    new winston.transports.File({ filename: 'logs/error.log', level: 'error' }),
  ],
});

// 사용
logger.info('User logged in', { userId });
logger.error('DB connection failed', { error: err.message });
```

> 🚫 `console.log` 사용 금지 (lint 경고). 디버그용은 `logger.debug`.

**🇺🇸 English**

**5.6 Logging**

Use `winston` for all server-side logging. `console.log` is banned (lint warning). Use `logger.debug` for development tracing, `logger.info` for normal events, and `logger.error` for failures. Never log sensitive fields (passwords, tokens).

## 6. 주석 (Comments)

### 6.1 좋은 주석 (WHY)

```typescript
// ✅
// MongoDB는 트랜잭션에서 같은 session을 모든 쿼리에 전달해야 한다.
// 누락하면 트랜잭션 밖에서 실행되어 격리가 깨진다.
await Document.updateOne({ _id }, update).session(session);

// ✅
// react-force-graph-3d는 nodes/links가 가변 ref여야 하지만,
// React strict mode에서 두 번 호출돼 좌표가 튀는 이슈가 있어 useMemo로 고정.
const graphData = useMemo(() => ({ nodes, links }), [nodes, links]);
```

**🇺🇸 English**

**6.1 Good Comments (WHY)**

Explain non-obvious decisions, workarounds, and constraints. The two examples above explain why `.session()` must be passed in MongoDB transactions, and why `useMemo` is used to stabilise graph data in React strict mode.

### 6.2 나쁜 주석 (WHAT — 코드가 이미 말함)

```typescript
// ❌
let count = 0;  // count를 0으로 초기화

// ❌
function getUser() {  // 사용자를 가져옴
  return user;
}
```

**🇺🇸 English**

**6.2 Bad Comments (WHAT — the code already says it)**

Do not narrate what the code obviously does. Redundant comments add noise and rot quickly when the code changes.

### 6.3 TODO 주석

```typescript
// TODO(BE1): 그래프 노드 수 100개 초과 시 LOD 적용 — W4 마무리
// FIXME(FE1): autocomplete 드롭다운 키보드 위쪽 이동 안 됨
// NOTE: 본 함수는 트랜잭션 안에서만 호출돼야 함
```

→ TODO는 `(담당자명)` 또는 GitHub Issue 번호 포함. 방치된 TODO 금지.

**🇺🇸 English**

**6.3 TODO Comments**

Every `TODO` must include an owner (member initial or GitHub issue number) and a target milestone. Unowned or unresolved TODOs are not allowed to linger past their milestone.

### 6.4 JSDoc (공개 API만)

```typescript
/**
 * 노트 내용에서 @/#/& 링크를 파싱하여 노드/관계 배열을 반환합니다.
 *
 * @example
 * parse("@엄마 #감정 &Child")
 * // → { mentions: ['엄마'], tags: ['감정'], pac: [{ role: 'Child' }] }
 */
export function parse(content: string): ParseResult { ... }
```

**🇺🇸 English**

**6.4 JSDoc (public APIs only)**

Add JSDoc blocks only on exported functions that are part of a module's public surface. Include at least one `@example`. Internal helpers do not need JSDoc.

## 7. 테스트

### 7.1 파일 위치

- 단위 테스트: `<file>.test.ts` (같은 디렉터리)
- 통합 테스트: `Backend/tests/` 또는 `Front/tests/`

**🇺🇸 English**

**7.1 File Location**

Unit tests live alongside the file under test as `<file>.test.ts`. Integration tests live in `Backend/tests/` or `Front/tests/`.

### 7.2 테스트 작성 패턴 (AAA)

```typescript
describe('linkParser', () => {
  it('parses @ mentions correctly', () => {
    // Arrange
    const input = '오늘 @엄마 와 통화함';

    // Act
    const result = parse(input);

    // Assert
    expect(result.mentions).toEqual(['엄마']);
  });

  it('returns empty arrays for plain text', () => {
    expect(parse('그냥 텍스트')).toEqual({
      mentions: [],
      tags: [],
      pac: [],
      relationships: [],
    });
  });
});
```

**🇺🇸 English**

**7.2 Test Pattern (AAA)**

Structure every test as Arrange → Act → Assert. Each `it` block tests exactly one behaviour. Use inline `expect` for trivial single-assertion cases.

### 7.3 describe/it 네이밍

- `describe('컴포넌트/함수명', ...)`
- `it('should ... when ...', ...)` 또는 한글로 자연스럽게

**🇺🇸 English**

**7.3 describe/it Naming**

`describe` takes the component or function name. `it` describes the expected behaviour in natural language — either English (`should return null when id is missing`) or Korean is acceptable, as long as it reads as a sentence.

## 8. 보안

### 8.1 절대 커밋 금지

- `.env`, `.env.local`
- API 키, JWT 시크릿
- 사용자 데이터 덤프
- 비밀번호 (평문이든 해시든)

**🇺🇸 English**

**8.1 Never Commit**

The following must never appear in commits: `.env` / `.env.local` files, API keys, JWT secrets, user data dumps, or passwords (plaintext or hashed).

### 8.2 입력 검증

- 모든 외부 입력은 서버에서 검증 (스키마 기반)
- SQL Injection (Mongoose 사용 시 자동 방지)
- XSS: React가 기본 escape, `dangerouslySetInnerHTML` 사용 시 sanitize-html
- CSRF: SameSite 쿠키 또는 토큰

**🇺🇸 English**

**8.2 Input Validation**

All external input must be validated server-side using schema-based validation. Mongoose prevents SQL injection by default. React escapes JSX output (no raw HTML without `sanitize-html`). Use SameSite cookies or CSRF tokens for state-mutating requests.

### 8.3 로깅 시 민감 정보 제외

```typescript
// ❌
logger.info('Login', { email, password });

// ✅
logger.info('Login', { email });
```

**🇺🇸 English**

**8.3 Exclude Sensitive Fields from Logs**

Never log passwords, tokens, full credit card numbers, or raw personal data. Log only the minimal identifiers needed to trace a request.
